\section{Introducción y Contexto del Proyecto}
% ===========================================================================

La máquina expendedora es un sistema embebido autónomo implementado en un
\textbf{Arduino Mega 2560}. Todo el firmware corre en un único microcontrolador
sin dependencias de red, corriendo sobre un \emph{super-loop} no bloqueante.

Los periféricos que gestiona el sistema son:
\begin{itemize}
    \item \textbf{Teclado matricial 4×4} (D22–D29) — entrada del usuario.
    \item \textbf{LCD 20×4 I$^2$C} (0x27) — retroalimentación visual.
    \item \textbf{Motores DC} vía PCA9685 (I$^2$C) — despacho de producto.
    \item \textbf{Lector RFID MFRC522} (SPI: D53, D8) — pago con tarjeta.
    \item \textbf{Sensor de puerta} (D3, pull-up) — seguridad física.
    \item \textbf{Barrera óptica de caída} (D2, pull-up) — confirmación de entrega.
    \item \textbf{EEPROM interna} — persistencia de inventario y caja.
\end{itemize}

El corazón del firmware es el módulo \texttt{VmFsm}, una Máquina de Estados
Finitos (FSM) con 13~estados que encapsula toda la lógica de negocio: selección,
cobro, despacho y cálculo de cambio.

% ===========================================================================
\section{Punto de Entrada: \texttt{main.cpp}}
% ===========================================================================

\subsection{Arquitectura de Super-Loop}

El firmware sigue el patrón \emph{bare-metal super-loop}: \texttt{setup()}
inicializa los periféricos una sola vez, y \texttt{loop()} se ejecuta
continuamente sin usar interrupciones ni RTOS.

\begin{lstlisting}[style=cpp, caption={Núcleo del super-loop en main.cpp}]
void setup() {
    Wire.begin();           // I2C antes del LCD y PCA9685
    display.begin();
    motor.begin();
    rfid.begin();
    fsm.begin();            // carga EEPROM y entra al estado S0
}

void loop() {
    char key = keypad.getKey();  // sondeo no bloqueante del teclado
    if (key != NO_KEY)
        fsm.handleKey(key);      // despachar tecla a la FSM

    fsm.update();                // avanzar la maquina de estados
}
\end{lstlisting}

\subsection{Inyección de Dependencias}

Todos los subsistemas se instancian como objetos estáticos globales y se
\emph{inyectan} al constructor de \texttt{VmFsm}:

\begin{lstlisting}[style=cpp, caption={Instanciación e inyección en main.cpp}]
static VmDisplay         display;
static VmEepromData      storage;
static VmMotorController motor;
static VmRfid            rfid;

static VmFsm fsm(storage, motor, rfid, onDisplay);
\end{lstlisting}

La función \texttt{onDisplay()} actúa como \emph{callback} de presentación:
la FSM nunca accede directamente al LCD; simplemente llama al puntero de
función \texttt{DisplayFn} que le fue entregado en construcción.

Este diseño desacopla la lógica de negocio del hardware físico y facilita
pruebas unitarias sin hardware real.

% ===========================================================================
\section{La Máquina de Estados: \texttt{VmFsm}}
% ===========================================================================

\subsection{Concepto y Rol}

\texttt{VmFsm} implementa el patrón \textbf{Mediador/Controlador}: centraliza
la lógica de negocio y coordina a los demás módulos sin que éstos se
conozcan entre sí.

Conceptualmente es una \textbf{Máquina de Moore}: las salidas (pantallas,
activación de motor, cálculo de cambio) dependen únicamente del estado actual,
y las transiciones dependen de eventos (teclas, lectura RFID, expiración de
temporizadores, señales de sensores).

\subsection{Mecanismo de Transición}

El flujo de control sigue un patrón de dos funciones complementarias:

\begin{enumerate}
    \item \texttt{enterState(FsmState next)} — cambia \texttt{\_state} y
          llama al gancho \texttt{onEnter*()} correspondiente que ejecuta
          las acciones de entrada al nuevo estado.
    \item \texttt{update()} — llamado cada ciclo desde \texttt{loop()}.
          Sondea temporizadores, sensores y el lector RFID para generar
          las transiciones temporizadas y autónomas.
\end{enumerate}

Las transiciones por teclado se procesan en \texttt{handleKey()}, que
traduce el carácter físico a una acción semántica mediante \texttt{VmKeypad}
y la delega al procesador de teclas del estado activo.

\subsection{Temporización No Bloqueante}

Todos los temporizadores se implementan comparando \texttt{millis()} contra
una referencia guardada, sin usar \texttt{delay()}:

\begin{lstlisting}[style=cpp, caption={Patrón de temporizador no bloqueante}]
// Arrancar el temporizador:
_motorTimer = millis();

// Verificar expiración (en update()):
if ((uint32_t)(millis() - _motorTimer) >= VM_TIMEOUT_MOTOR_MS) {
    // ... acción de timeout
}
\end{lstlisting}

El cast a \texttt{uint32\_t} garantiza el manejo correcto del desbordamiento
(\emph{overflow}) del contador de 32 bits cada 49 días.

Los timeouts definidos son:

\begin{table}[H]
\centering
\begin{tabular}{lrp{5.5cm}}
\toprule
\textbf{Constante} & \textbf{Valor} & \textbf{Uso} \\
\midrule
\texttt{VM\_TIMEOUT\_INACTIVITY\_MS} & 180\,000 ms & Regreso a reposo por inactividad en S3–S6 \\
\texttt{VM\_TIMEOUT\_MOTOR\_MS}      &  10\,000 ms & Tiempo máximo de giro del motor en S8 \\
\texttt{VM\_CAROUSEL\_INTERVAL\_MS}  &   2\,000 ms & Rotación de subpantalla del carrusel \\
\bottomrule

\end{table}

\subsection{Seguridad Física: Sensor de Puerta}

Antes de girar el motor se verifica que la puerta del cajón esté cerrada.
El sensor está en D3 con nivel activo \texttt{LOW}. Para evitar falsos
positivos por rebotes mecánicos, se implementa un filtro de debounce de 30 ms:

\begin{lstlisting}[style=cpp, caption={Filtro de rebote en updateDoor()}]
void VmFsm::updateDoor() {
    bool level = (digitalRead(VM_PIN_DOOR) == VM_DOOR_CLOSED_LEVEL);
    if (level != _doorSampled) {
        _doorSampled      = level;
        _doorLastChangeMs = millis();
    } else if ((uint32_t)(millis() - _doorLastChangeMs) >= VM_DOOR_DEBOUNCE_MS) {
        _doorStable = level;  // estado estable confirmado
    }
}
\end{lstlisting}

\section{Cálculo de Cambio: \texttt{VmChangeCalculator}}
% ===========================================================================

\subsection{Algoritmo Greedy Decreciente}

El cambio se calcula con un \textbf{algoritmo voraz} (\emph{greedy}): se
intentan primero las monedas de mayor denominación, reduciendo el monto
restante hasta completarlo o agotar las existencias.

Las denominaciones utilizadas (en centavos de peso mexicano) son:

\begin{center}
\$10.00 (1000¢) \quad \$5.00 (500¢) \quad \$2.00 (200¢) \quad \$1.00 (100¢)
\end{center}

\begin{lstlisting}[style=cpp, caption={Núcleo del algoritmo greedy en VmChangeCalculator::calculate()}]
const uint32_t denominaciones[4] = { 1000u, 500u, 200u, 100u };

for (uint8_t i = 0; i < 4 && total > 0u; i++) {
    uint32_t disponible = 0;
    cashBox.getCoinStock(denominaciones[i], disponible);

    uint32_t usar = 0;
    while (usar < disponible && total >= denominaciones[i]) {
        total -= denominaciones[i];
        usar++;
    }

    if (usar > 0u) {
        cashBox.deductCoins(denominaciones[i], usar);
        *contadores[i] = usar;
    }
}

if (total > 0u) return false;  // cambio no realizable
\end{lstlisting}

\subsection{Decisiones de Diseño}

\begin{itemize}
    \item \textbf{Aritmética entera en centavos}: los precios y montos se
          almacenan como \texttt{uint32\_t} en centavos para evitar errores
          de punto flotante en el AVR de 8~bits.
    \item \textbf{Consulta antes del descuento}: se consulta
          \texttt{getCoinStock()} antes de descontar, garantizando que nunca
          se descuente más de lo disponible.
    \item \textbf{Integración con EEPROM}: cada \texttt{deductCoins()} persiste
          inmediatamente en EEPROM, de modo que ante un corte de energía la
          caja refleja el estado real.
    \item \textbf{Retorno \texttt{false} si no hay fondos}: la FSM muestra un
          mensaje informativo y regresa a reposo tras 5~s sin intentar ningún
          pago forzado.
\end{itemize}

\subsection{Invocación desde la FSM}

El cálculo se inicia en el estado \textbf{S11\_CALC\_CAMBIO} solo si el pago
fue en efectivo y si $\text{insertado} > \text{precio}$:

\begin{lstlisting}[style=cpp, caption={Llamada al calculador en onEnterCalcCambio()}]
void VmFsm::onEnterCalcCambio() {
    uint32_t cambio = _insertedCentavos - _slotInfo.priceCentavos;
    if (cambio == 0u) {
        enterState(FsmState::S12_PANTALLA_FIN); return;
    }
    bool ok = _changeCalc.calculate(_insertedCentavos,
                                    _slotInfo.priceCentavos,
                                    _data, _changeResult);
    if (!ok) { /* mostrar error y esperar 5 s */ return; }
    enterState(FsmState::S12_PANTALLA_FIN);
}
\end{lstlisting}

\subsection{Descripción Detallada de Cada Estado}

\paragraph{$S_0$ — Arranque.}
Se muestra un mensaje de bienvenida mientras \texttt{begin()} carga la EEPROM.
Si los datos son válidos, la transición a $S_2$ ocurre en el primer ciclo de
\texttt{update()}.

\paragraph{$S_1$ — Falla Interna.}
Estado terminal alcanzado si \texttt{VmEepromData::begin()} devuelve
\texttt{false}. El sistema muestra un error permanente y no acepta ninguna
entrada. Requiere reinicio físico.

\paragraph{$S_2$ — Reposo.}
Estado de espera de largo plazo. El carrusel rota mostrando dos productos
por subpantalla cada 2~s. Es el destino de retorno de todos los flujos de
error, cancelación y éxito.

\paragraph{$S_3$ — Selección de Canal.}
Se consulta \texttt{VmEepromData::getSlot()} para verificar que el slot
está habilitado. Si no, regresa a $S_2$ inmediatamente. Muestra nombre
del producto y precio. La tecla \texttt{A} confirma.

\paragraph{$S_4$ — Selección de Pago.}
El usuario elige la pasarela de cobro. Si selecciona RFID pero el lector no
está disponible (\texttt{rfid.isAvailable()} devuelve \texttt{false}),
se muestra aviso y se permanece en la pantalla de selección.

\paragraph{$S_5$ — Espera de Efectivo.}
Las teclas 1–9 representan monedas de \$1 a \$500. Cada pulsación llama a
\texttt{addCoins()} en EEPROM y actualiza el acumulado \texttt{\_insertedCentavos}.
Cuando el acumulado cubre el precio, se transita automáticamente a $S_7$.

\paragraph{$S_6$ — Espera de RFID.}
\texttt{VmRfid::poll()} se llama en cada ciclo sin bloquear. Si la lectura
es exitosa, se verifica el saldo. Si es suficiente, se llama a
\texttt{deductBalance()} y se transita a $S_7$. Si el saldo es insuficiente
o hay error de lectura, se muestra un mensaje y se regresa a $S_2$.

\paragraph{$S_7$ — Reservada.}
Punto de no retorno transaccional. Se ejecuta en orden:
(1) \texttt{reserveStock()} — decrementa inventario;
(2) \texttt{beginOrder()} — persiste en EEPROM que hay una orden en curso;
(3) Se verifica \texttt{\_doorStable} (puerta cerrada);
(4) \texttt{motor.start()} — verifica que la barrera esté libre y enciende el motor.
Si cualquier condición falla, se transita a $S_{10}$.

\paragraph{$S_8$ — Dispensando.}
En cada ciclo de \texttt{update()}, se consulta \texttt{motor.isBusy()}.
Cuando la barrera óptica detecta la caída del producto,
\texttt{VmMotorController} detiene el motor y pone el resultado en
\texttt{consumeResult()}. Un timeout de 10~s protege contra atascos.

\paragraph{$S_9$ — Confirmada.}
Se llama a \texttt{completeOrder()} para cerrar el registro transaccional
en EEPROM. La pantalla de éxito se muestra 1~s antes de avanzar a $S_{11}$
(efectivo) o $S_{12}$ (RFID, sin cambio).

\paragraph{$S_{10}$ — Falla de Despacho.}
Si \texttt{\_stockReserved} es \texttt{true}, se deshace la operación:
\texttt{completeOrder()} con el resultado de falla y \texttt{releaseStock()}
devuelven el inventario. El mensaje de error dura 3~s y retorna a $S_2$.

\paragraph{$S_{11}$ — Cálculo de Cambio.}
Invoca \texttt{VmChangeCalculator::calculate()} que aplica el algoritmo
greedy y descuenta las monedas usadas de la EEPROM. Si no hay fondos
suficientes, se muestra aviso y se espera 5~s antes de volver a $S_2$.

\paragraph{$S_{12}$ — Pantalla Final.}
El carrusel muestra dos subpantallas: la primera confirma la compra, la segunda
detalla las monedas de cambio (o el cobro RFID). Tras dos intervalos de 2~s
más 1~s de margen, retorna a $S_2$.

\section{Conclusiones}
% ===========================================================================

El diseño de la FSM cumple los objetivos de un sistema embebido robusto:

\begin{enumerate}
    \item \textbf{Legibilidad lineal}: los 13 estados están numerados
          secuencialmente $S_0$–$S_{12}$ y el código fuente sigue el mismo
          orden de arriba a abajo, facilitando la lectura y el mantenimiento.
    \item \textbf{Sin sobreingeniería}: cada clase tiene una responsabilidad
          única y bien delimitada. La FSM no accede directamente al hardware;
          toda comunicación es a través de las interfaces de los subsistemas.
    \item \textbf{Robustez ante cortes de energía}: el estado transaccional
          de cada orden se persiste en EEPROM en $S_7$ (\texttt{beginOrder})
          y se cierra en $S_9$/$S_{10}$ (\texttt{completeOrder}), garantizando
          consistencia aunque la alimentación se corte durante el despacho.
    \item \textbf{Temporización no bloqueante}: todos los delays del sistema
          se implementan con \texttt{millis()}, permitiendo que el super-loop
          permanezca siempre receptivo a eventos externos.
    \item \textbf{Trazabilidad de fallos}: el estado $S_{10}$ y la variable
          \texttt{\_pendingResult} permiten distinguir tres causas de falla
          de despacho y presentar mensajes diferenciados al usuario.
\end{enumerate}
